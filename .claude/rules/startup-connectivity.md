### Startup connectivity gating (splash screen + Wi-Fi setup)

The app doesn't show its normal UI until real internet access is confirmed. `main.qml`'s root `Window` has a small state machine (`appState`: `"splash"` | `"wifiSetup"` | `"ready"`) that decides what's on screen; `mainRec` (the existing `SwipeView` + settings drawer + drag handle — the whole "real app") is never unmounted or re-parented, it's simply painted over: `SplashScreen` and `WifiSetupPage` are declared as `Window`-level siblings *after* `mainRec`, so whichever is `visible` paints on top of everything inside it. Every provider above `mainRec` (`TimeDateProvider`, `LocationProvider`, `WeatherProvider`, `ReminderManager`) keeps running the whole time — gating *their* startup too would add real complexity for a window that's normally only covered for ~2 seconds plus one HTTP round trip.

**The state machine, in `main.qml`:**
- `splashMinTimeElapsed` (bool) flips true once, from a one-shot 2000ms `Timer` (`splashMinTimer`) — this is where the "~2 seconds" requirement actually lives.
- `evaluateAppState()` is the single place that decides `appState`: stays `"splash"` while `!splashMinTimeElapsed || connectivityChecker.checking`; becomes `"ready"` if `connectivityChecker.online`; otherwise `"wifiSetup"`. Called from both `splashMinTimer.onTriggered` and a `Connections { target: connectivityChecker; function onCheckFinished() }` block, so *either* condition finishing later than the other still re-evaluates correctly (a slow connectivity check doesn't get stuck showing splash forever once the timer's already fired, and a fast check doesn't skip the 2s minimum).
- `connectivityChecker.checkNow()` is called once from its own `Component.onCompleted` (matching `LocationProvider`'s existing `Component.onCompleted { fetchLocation() }` convention) — nothing auto-starts a check from C++ itself.

**`ConnectivityChecker`** — one job: is there *actual internet*, not just an up network interface (a device can be associated with a router that itself has no WAN). Fires a single `QNetworkAccessManager` GET at Google's `generate_204` endpoint (the same technique Android/ChromeOS use internally for captive-portal detection — a 204 response has no body to download, so only "did this succeed at all" is checked), with a 4s timeout via a sibling `QTimer` that `abort()`s the pending reply on expiry. Exposes `online`/`checking` plus a `checkFinished(bool)` signal. `checkNow()` no-ops while already checking, so both the startup call and any later "recheck after Wi-Fi connect" / manual "Retry" call are safe to fire without the caller tracking in-flight state itself.

**`WifiManager`** — abstract on purpose. Unlike every other provider in this app, there's no cross-platform way to scan/join Wi-Fi networks — Qt/QML has no built-in API for it (this is fundamentally different from the plain HTTP calls `LocationProvider`/`WeatherProvider`/`ConnectivityChecker` make, which behave identically on any OS). `WifiManager.h` owns all the QML-facing state (`networks`, `scanning`, `connecting`, `status`, `errorString`) and the two public entry points (`scanNetworks()`, `connectToNetwork(ssid, password)`), but both just set the busy flag and defer to a pure-virtual `startScan()`/`startConnect()` — implemented exactly once each by a concrete platform subclass. `CMakeLists.txt`'s `if(WIN32)` block compiles in exactly one of `WifiManagerLinux.cpp`/`WifiManagerWindows.cpp`; `main.cpp` registers whichever one was compiled under the same QML type name (`"WifiManager"`) — the identical "swap the concrete class, keep the interface" pattern this codebase already uses for `FlightDataSource`/`OpenSkyFlightSource`. `WifiSetupPage.qml` never knows or cares which subclass it's actually talking to.

- **`WifiManagerLinux`** — the real deployment target (Raspberry Pi OS). Shells out to `nmcli` via `QProcess`: `nmcli -t -f SSID,SIGNAL,SECURITY dev wifi list --rescan yes` to scan (`-t` terse/colon-separated output is stable across nmcli versions, unlike its human-readable table), `nmcli dev wifi connect "<ssid>" password "<pass>"` to join. `parseScanOutput()` handles `nmcli`'s `\:`-escaped colons within a field (so an SSID that happens to contain a literal colon doesn't corrupt the split) and de-duplicates by SSID (the same AP can appear once per band/radio).
- **`WifiManagerWindows`** — this app's dev/test platform (per `CLAUDE.md`'s build notes), *not* the deployment target. Shells out to `netsh wlan` instead of raw `WlanAPI` C++ bindings, to keep the same "QProcess + parse text" shape as the Linux side rather than mixing approaches. Scanning parses `netsh wlan show networks mode=bssid`'s output. Connecting is two `netsh` calls, not one: `netsh` has no "join this SSID with this password" command for a brand-new network, only for joining a *profile* Windows already knows about — so `startConnect()` first writes a temporary WLAN profile XML (`buildProfileXml()`, WPA2-PSK/AES if a password was given, `open`/`none` if not) to a `QTemporaryFile`, runs `netsh wlan add profile filename="..."`, and only on success runs `netsh wlan connect name="<ssid>"` as a second `QProcess`. **Two known limitations, documented in the class's own header comment, not bugs to silently fix later:**
  - `netsh`'s scan output is human-readable text, *localized to the Windows display language* — `parseScanOutput()`'s regexes match the English field names (`SSID`, `Authentication`, `Signal`) and need adjusting on a non-English install. `nmcli -t`'s terse mode has no equivalent problem.
  - New secured profiles are always built as WPA2-Personal (PSK/AES) — covers ordinary home/small-office Wi-Fi, not WPA3-only or enterprise (802.1X) networks.
- **Passwords are never persisted by this app.** They're handed to `nmcli`/`netsh` and from there it's the OS's own network stack that remembers them going forward (or doesn't, per the user's own OS settings) — same as joining Wi-Fi through the OS's native settings UI, not a new app-side secret store.
- **Permissions are not guaranteed frictionless.** Adding a *new* Wi-Fi profile can require elevated/administrator rights on some Windows configurations, and `nmcli`'s ability to modify NetworkManager connections depends on the running user's polkit/`netdev`-group permissions on Linux. Neither has been verified against a specific locked-down deployment; expect to need to adjust for whatever the actual target machine's policy turns out to be.

**`SplashScreen.qml`** — purely presentational (`checking: bool` is its only input, just swaps the status line's wording); has no idea what happens after it, that's `main.qml`'s `evaluateAppState()` alone. The spinner is a rotating ring `Rectangle` with a small background-colored notch cut out of the top — a *uniform* rotating circle wouldn't visibly read as spinning at all, and a real arc would need `QtQuick.Shapes` (already used elsewhere, e.g. `utilities/HorizonLine.qml`) for what's ultimately a two-second cosmetic flourish, so the notch trick was cheaper.

**`WifiSetupPage.qml`** imports `QtQuick.Controls.Basic` alongside plain `QtQuick.Controls` — its Rescan/Retry/Cancel/Connect `Button`s customize `background`, which throws `"The current style does not support customization of this control"` at runtime without it (see `CLAUDE.md`'s general note on this; `Brightness-Control/BritnessControl.qml` and `utilities/CustomButtonIcon.qml` hit the same thing first).

**`WifiSetupPage.qml`** — two steps in one file, toggled by `selectedNetwork` being `null` or not: a network list (`ListView` over `wifiManager.networks`, Rescan/Retry buttons) and a password entry (`TextField`, Connect/Cancel). Text fields use the system physical keyboard; there is no in-app virtual keyboard. **A plain background `Rectangle` does not block mouse input** — a real bug class worth flagging explicitly, since it's easy to assume "it's opaque and on top" is enough: without an explicit full-fill `MouseArea` declared *before* the page's real controls (so those controls still paint on top and keep first claim on their own clicks), a tap on empty space here would fall straight through the whole page to `mainRec`'s `SwipeView` underneath, defeating the entire point of this page blocking the app while offline.

**Wi-Fi connect → back to `ready`.** `WifiSetupPage` listens for `wifiManager.connectionResult(success, error)`; on success it clears its own `selectedNetwork` and calls `connectivityChecker.checkNow()` — it does **not** set `appState` itself (it doesn't know that property exists). `main.qml`'s existing `Connections { target: connectivityChecker; function onCheckFinished() }` is what actually moves `appState` to `"ready"` once that recheck confirms real internet, keeping "did Wi-Fi join succeed" and "is there actually internet" as two separate questions the same way the initial startup check does.
